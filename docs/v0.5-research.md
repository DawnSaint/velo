# v0.5.x 开发前调研：工作区与文件管理

> **性质**：pre-implementation 设计研究，候选方案尚未拍板。定稿后取舍进 `DECISIONS.md` ADR，本文档随之删除。
> **对应 ROADMAP**：v0.5.0（侧边栏文件树 / 工作区）/ v0.5.1（资产面板）/ v0.5.2（大纲搜索 / 状态栏）。
> **调研日期**：2026-06-22。

---

## 0. 范式跳跃

v0.4.x 是"单文件编辑器"：`documentStore` 围绕一个 `currentFilePath` 转，fs:watch 单句柄，持久化只存当前文件相关状态。v0.5.x 跳到"目录级工作区"：文件树要反映外部增删改、要记最近文件 / 工作区根 / 展开状态、资产面板要聚合多文件引用。下面 5 块按"现状 / 候选 / 取舍 / 建议 / 待定"展开。

---

## 1. fs.watch 多目录生命周期（对应 ARCHITECTURE 维护者注意点 #2）

### 现状
`stores/document.ts` 单 `unwatch: UnwatchFn | null` 句柄。`startWatchOf(path)` 先 `await stopWatch()` 再 `await watch(path, cb, { delayMs: 100 })`，stop 与新 watch 之间有 async gap。单文件场景靠 App.vue window-focus 调 `checkExternalChange` 兜 notify-rs 漏报，gap 无实际影响。

### 候选
- **A. 工作区根一个 recursive watch**：`watch(rootDir, cb, { recursive: true, delayMs })`，1 个句柄，notify-rs `delayMs` 合并 burst。文件树刷新走 cb → `readDir` 重拉变更子树。
- **B. 逐目录懒 watch**：展开一个目录挂一个 watch，折叠 `unwatch`，`Map<dir, UnwatchFn>` 管理多句柄。

### 取舍
- A 简单（生命周期仍是单句柄，沿用现有 start/stop 模式），但深目录树事件量大（即便 `delayMs` 合并，cb 触发后要重拉整树或做 path diff）。
- B 事件量精准，但多句柄生命周期管理引入 #2 race 的真实风险：用户快速展开/折叠时 `await stopWatch` / `await watch` 交错，句柄泄漏或回调串台。需要 per-dir 的 stop-before-start 串行化（队列化），复杂度跳一档。
- A 与现有 `documentStore` 的单文件 watch 语义可统一：工作区根 watch 负责树刷新，当前文件 watch（已有）负责内容 external-change，两套互不干扰。

### 建议
**v0.5.0 走 A**：recursive 单 watch 句柄挂在工作区根，cb 只做"标记某子树脏 + 防抖重拉"，不做精细 path diff。B 留作 v0.5.x 后期深树性能问题的备选，不预先做。

### 待定
- 当前文件 watch 与工作区根 watch 共存时，当前文件也在根树下，会收到两份事件——需要确认 `checkExternalChange` 的去重（已有 `externalCheckInFlight` 重入保护应够，但要验证 cb 不会在树刷新路径上重复触发文件内容检查）。
- notify-rs 对网络盘 / 同步工具（OneDrive / Dropbox）的已知漏报在目录级是否更严重——window-focus fallback 是否要扩到"重拉整树"。

## 2. `src/tauri/` 封装层（对应 TESTING.md §4）

### 现状
`src/tauri/` 不存在。`persistence.ts` 事实上已在做 fs 薄封装：统一 `tauriOnly()` 守门、统一 try/catch 降级、覆盖 readDir/remove/rename/mkdir/exists/readTextFile/writeTextFile/watch。`document.ts` 则直接 import `@tauri-apps/plugin-fs` 的 `readTextFile/writeTextFile/watch`。测试 mock 直接打在 `@tauri-apps/plugin-fs`（`src/test/setup.ts`）。

### 候选
- **A. 建 `src/tauri/{fs,dialog,path}.ts` 统一封装，业务侧只 import 封装**：`src/tauri/fs.ts` 暴露 `readDir / readTextFile / writeTextFile / mkdir / remove / rename / exists / watch`（含 `tauriOnly` 守门 + 统一错误形态），`persistence.ts` / `document.ts` / 新文件树 store 都走它；测试 mock 打在 `src/tauri/*`，`@tauri-apps/*` 从业务代码里消失。
- **B. 不建封装，沿用现状**：新文件树 store 直接 import `@tauri-apps/plugin-fs`，mock 散落打在 `@tauri-apps/*`。

### 取舍
- A 一次重构成本（迁移 `persistence.ts` / `document.ts` 现有调用点），换 E2E 就绪（TESTING.md §4 明确收敛目标）+ 测试 mock 单一入口 + web dev 端 `tauriOnly` 行为统一。
- B 零成本，但 v0.5.x 会新增大量 fs 调用（目录遍历、批量重命名、资产移动），不收敛则 mock 散布、后续接 tauri-driver E2E 时返工。

### 建议
**v0.5.0 第一个 PR 建 `src/tauri/fs.ts` 作为基建**，先把 `persistence.ts` 的事实封装抽过去（`persistence.ts` 退化为"settings / outline / draft 业务逻辑"，IO 调 `src/tauri/fs`），`document.ts` 的 fs 调用一并迁。新文件树 store 从一开始就只 import `src/tauri/*`。`dialog.ts` / `path.ts` 视迁移过程中遇到的调用点再补，不预先建空壳。

### 待定
- 封装层错误形态：现在 `persistence.ts` 各函数失败策略不一（load 返 null / save 仅 log / draft 原子写）。封装层是统一抛 typed error 让调用方决定，还是保留各自降级？倾向封装层抛 `VeloFsError`，降级策略留在业务层（persistence 保持自己的降级语义）。
- `watch` 的封装：`UnwatchFn` 类型要不要在封装层重新导出，避免业务层再 import `@tauri-apps/plugin-fs` 拿类型。

## 3. capability scope 收紧（对应 ARCHITECTURE 维护者注意点 #3）

### 现状
`capabilities/default.json` 已开 `read-text-file / write-text-file / exists / watch / unwatch / mkdir / write-file / read-file / read-dir / remove / rename`，全部 `allow: [{ path: "**" }]`。文件树所需权限**已齐**，v0.5.0 不存在"要补权限"的阻塞。

### 候选
- **A. 保持 `**`，UI 层做约束**：本地单用户桌面应用，威胁模型是"用户主动打开的文件"，`**` 不 worsen；destructive op（删除 / 重命名 / 移动）在 UI 层加确认对话框即可。
- **B. Rust 自定义 command + 服务端路径校验**：放弃 plugin-fs 直连，所有 fs op 走自写 Tauri command，在 Rust 侧校验路径必须在工作区根内。安全性最高，但等于重写 fs 访问层，且 v0.5.0 文件树/资产面板所有调用点都要换。
- **C. 动态 capability / scope 变量**：Tauri 2 fs scope 是静态 glob，不支持引用运行时选的工作区根路径，无法直接表达"仅当前工作区根"。技术上要 C 必须退化成 B。

### 取舍
- A 与现状一致，零成本。本地编辑器（对标 Typora / Obsidian）的 fs scope 本就是 `**`，分发收紧优先级低。
- B 只在"应用要处理不可信工作区 / 多租户"时才有意义，Velo 不是。

### 建议
**走 A**：`**` 保持，分发版不收紧 scope。安全性靠 UI 确认对话框（删除文件 / 移动资产前 confirm）。把"scope 不收紧"作为一条 ADR 记下理由（避免后续反复被"应该收紧"的直觉推翻）。

### 待定
- 资产面板"重新组织"（v0.5.1）若要复制图片到工作区内 `assets/` 目录，需要 `fs:allow-copy`——当前 capability 没有，届时补。
- `fs:allow-stat`（拿文件大小 / 修改时间做资产面板展示）也未开，届时按需补。

## 4. 持久化结构扩展

### 现状
`appDataDir/` 下：`velo-settings.json` / `velo-outline-state.json` / `drafts/{id}.json`。命名约定 `velo-{name}.json` + 顶层 `version` 字段 + load/save 配对函数（在 `persistence.ts`）。

### 候选
v0.5.x 要持久化的新状态：
- **最近文件列表**（v0.5.0 "打开最近文件"）：路径数组，定长截断（如 20）。
- **工作区根记录**（v0.5.0 "工作区概念"）：历史工作区根路径 + 上次激活的一个。
- **文件树展开状态**（v0.5.0 "记录展开状态"）：每个工作区根下展开的目录路径集合。

### 取舍
- 最近文件单独 `velo-recent-files.json`（跨工作区，全局）。
- 工作区根 + 该工作区的展开状态合并进 `velo-workspaces.json`（展开状态是工作区局部状态，分开存反而要双 key join）。
- 大纲折叠状态（已有 `velo-outline-state.json`，按文件 path 存）是否要迁进 per-workspace？倾向不迁——大纲折叠是 per-file 状态，与工作区无关，跨工作区打开同一文件仍应记住折叠，保持现状。

### 建议
新增两个文件，沿用 `velo-{name}.json` + `version` 约定：
```
velo-recent-files.json   { version, files: string[] }              // 全局，截断 20
velo-workspaces.json     { version, active: string, workspaces: {
                            [rootPath]: { expandedDirs: string[] } } }
```
load/save 配对函数加在 `persistence.ts`（或 v0.5.0 的新 `workspaceStore`，但 IO 仍走 `src/tauri/fs`）。

### 待定
- 工作区记录是否要存"上次打开的文件"（恢复工作区时自动打开上次的文件）——倾向存，放进 `workspaces[rootPath].lastFile`。
- 最近文件列表去重策略（同路径不同大小写在 Windows 同文件）。

## 5. 侧边栏骨架（v0.5.0 第一个 PR 的骨架）

### 现状
`App.vue` 当前布局：顶栏 + `EditorOutline.vue`（独立侧栏，只渲染大纲）+ 编辑器。大纲折叠状态走 `outlineStore`。

### 候选
- **A. 侧边栏 tab 切换组件**：新建 `Sidebar.vue`（或改造 `EditorOutline.vue` 为 `SidebarTab`），顶部 tab 切"大纲 / 文件树"，两份内容 `v-if` 互斥，共享同一侧栏宽度。文件树 tab 内容由新 `workspaceStore` + `FileTree.vue` 驱动。
- **B. 大纲与文件树并存（双面板）**：侧边栏同时显示，纵向分割。空间利用率低，与 ROADMAP "二者可切换" 不符。

### 取舍
- A 符合 ROADMAP v0.5.0 "侧边栏统一收纳大纲与文件树，二者可切换"。
- tab 状态（当前看大纲还是文件树）是否持久化？倾向持久化到 `velo-workspaces.json` 的 per-workspace 状态（或全局 settings），用户切回工作区恢复上次看的 tab。

### 建议
**走 A**。具体骨架在 v0.5.0 开工时进 plan mode 出方案（涉及 `App.vue` 布局改动 + `workspaceStore` 设计 + `FileTree.vue` 虚拟化策略——大目录是否要虚拟滚动留作 plan 时评估）。

### 待定
- 文件树大目录性能（单目录上千文件）：先不虚拟化，`readDir` 一次性拉 + DOM 渲染，性能不够再加虚拟滚动。
- 拖入文件打开（v0.5.1）与现有 `imageUploadPlugin.handleDOMEvents.drop` 的关系——文件树拖入编辑器要区分"拖 md 文件 = 打开"vs"拖图片 = 插入"，源码模式 `forbidFileDropPaste` 也要协同。
