# Editor Architecture

> **本文件负责**: ProseMirror / CodeMirror 编辑器栈、markdownIO、语法实时转换、NodeView/Decoration、mermaid、shiki 与跨模式同步。
>
> **何时阅读**: 改 schema、markdownIO、ProseMirror 插件链、NodeView/Decoration、代码高亮、源代码模式、快捷键或新增 markdown 语法（见下方「新增语法支持 checklist」）时。
>
> **先记住**:
> - `allPlugins` 的加载顺序由 `plugins/order.ts`（CANONICAL_PLUGIN_ORDER）+ `resolvePlugins` 解析器决定，`EditorInner.vue` 中 `pluginEntries` 的物理顺序无关。新增 / 删除 / 重命名插件必须同时改 `order.ts`，否则解析器抛集合不匹配错误。
> - **`foldDecoration` 必须排在 `codeHighlight` / `codeLineNumber` / `mermaidDecoration` / `tocDecoration` 之前**（`CANONICAL_PLUGIN_ORDER` 的「Code Decorations」段）。`foldDecoPlugin.apply` 在 apply 阶段整体刷新 module-level 的 `ancestorFoldedCodeBlockPosSet` / `foldedMermaidPosSet` / `foldedTocPosSet`,下游 consumer 的 `apply` 若在同事务内读这套集合做增量重建,需保证 fold 已先刷新。注意:PM 实际渲染顺序是「全部 plugin.apply 跑完 → 才逐个调 `decorations(state)`」,故 consumer 在 `decorations` 里读到的一定是本帧最新集合,apply 顺序只影响「consumer 在自身 `apply` 增量重建时读集合」这一窄路径(例如 code block 落在 dirty range 内的文本插入)。把 `foldDecoration` 前置是消除该时序风险、与「consumer 必须看到最新 set」设计意图一致的保守排序,由 `foldCrossPlugins.test.ts` 的不变量用例锁定。祖先折叠时 header 抑制的真正门控是 `isCodeBlockAncestorFolded(pos)`(见下「块级折叠」设计要点),与 plugin 顺序无直接因果。
> - mermaid / TOC 走 Decoration.widget，不走 NodeView；不要 dispatch setMeta 触发 mermaid widget rebuild。
> - shiki dark/light 翻面走 CSS；换主题 / 懒加载 lang 才触发受控 rebuild。
> - syntaxAutoFormat 的 apply 直接改框架传入的 `tr`，不要自己 dispatch。
> - markdownIO 双向改动必须补/跑 round-trip。
>
> **相关文件**: [架构入口](../ARCHITECTURE.md) / [查找替换](./find-replace.md) / [导出](./export.md)


## 禁令速查

- 不要 `dispatch setMeta` 触发 mermaid / shiki 重建；mermaid 直接写 widget DOM，shiki darkMode 纯 CSS。
- 不要用 `getLanguage()` 探活 shiki miss；用 `getLoadedLanguages()`。
- 不要把脚注编号写回 `attrs.label`。
- 快捷键不要在 `EditorInner.vue` 硬编码，走 `editor/shortcuts/bindings.ts`。
- `[TOC]` 回写 toMarkdown 不要用 text 节点。
- 不要清理 `getTokensCached` 这层 LRU。

## 设计要点

- **mermaid 走 Decoration.widget 不走 NodeView**: atom NodeView 的 outer dom `innerHTML` 变更会被 ProseMirror DOMObserver 当外部突变 → 全量 remount + 每字符 loader 闪烁;widget 的 `ignoreMutation` 默认忽略非 selection 突变。当前 `mermaid` 节点已废弃,```` ```mermaid ```` 改走 `code_block { language: 'mermaid' }`,由 `MermaidDecoration` 扫 code_block 渲染 SVG widget + 自管切换/删除/关闭按钮(默认 pre 隐藏,SVG `side:-1` 渲染在其前;点击 SVG 派发 setMeta 翻转 editNodePos,展开时 `queueMicrotask` 把光标放进 pre)。**坑**: plugin promise resolve 后不要 dispatch setMeta rebuild decorations,直接在 widget dom 上写 svg,否则 `WidgetType.eq` 失效 → 死循环;主题切换同理走 window listener 自改 dom + `spec.destroy` removeEventListener 防泄漏。PM 搜索命中隐藏的 mermaid 源码时,必须先走幂等展开 helper 再做 `TextSelection` / `coordsAtPos` / 滚动;不要直接 blind toggle,否则已展开块会被收起,或 Mermaid 自带 pending focus 抢走搜索选区
- **mermaid + codeHighlight 双 plugin 分工**: codeHighlight 对普通 code_block 出 header 标题栏(折叠 chevron + 语言选择 + 复制)+ 语法高亮;mermaid 的 header **联动展开态** —— 收起态(显示 SVG / 源码隐藏,`editNodeSet` 不含本 pos)跳过 header,避免与 MermaidDecoration 的 SVG + 切换/删除 toolbar 叠双层;展开态(源码可见)仍保留 header(语言选择 + 复制可用),但 **fold chevron 隐藏**(`hideFoldBtn = mermaidExpanded`)—— 避免手闲点 fold 误触发 `FoldDecoration` 折叠 code_block → `isMermaidFolded` 把 SVG 也吞掉;mermaid 的"收"由 mermaid toolbar toggle 承担,header 提供 fold 入口只会有害。`renderHeader = !isMermaid || editNodeSet.has(pos + 1)`。与 `CodeLineNumberWidget`("mermaid code_block → 无行号")同范式。跳 header / 藏 chevron 都只是跳过 UI 容器,token 着色旁路(见下一条)始终 fall through
- **mermaid 语法高亮旁路 shiki**: shiki bundled mermaid grammar 薄(只输出按行纯文本 token),`codeHighlight` 对 `lang==='mermaid'` 走自写 `tokenizeMermaid`(6 类:keyword/direction/shape/edge/label/comment),颜色从当前代码块主题按 TextMate scope 提取 hex 写进 `--shiki-light/dark` 局部变量(同 shiki token 形态);主题切换/dark 切换两条路径同 shiki

  代码块 `<pre><code>` 的 `line-height: 1.6` × `font-size: 0.9em(14.4px)` = **23.04px**;文本位置 caret = font logical height **14px**;末行 separator/br 处的 caret = **23.04px**(`max(14.4 separator box, 23.04 line box)`)。差 = 9.04px(≈ 0.63 × font-size),"明显高一点"。同样的机制也出现在 `fold_placeholder` 的 `...` 处:折叠 placeholder 是 inline atom(`display: inline-block; font-size: 1em`,继承 h2 的 `line-height: 1.75`),在 h2 里 element box 高 = 1.75 × 25.6 = 44.78px ≈ line box 44.8px → 紧贴 `...` 的 caret = 44.8px,同段文本位置 caret = font logical **34px**,差 = 10.8px(≈ 0.42 × font-size),"明显更高"。**根因不是 fix 也不是 fold_placeholder 自身**,是 Blcok 的 line box 在非文本位置压倒了文本位置的 em-square caret。**为什么 fix 不能消灭这个差**:line box 由**块级 `line-height`** 决定(`<pre>`、`<code>` 的 1.6,h2 的 1.75),无法对单行单独缩小;把 separator 的 `height: 1em` 改 0/1px 都不影响 line box(实测:no-fix 版 separator 0×0、line box 仍是 23.04,光标仍 23.04)。**当前处理**:`customCaretPlugin`(详见下方设计要点)接管非文本位置 —— 用 `view.coordsAtPos` 拿到行网格上的 em-square 高度 rect,画一根 1px `currentColor` 覆盖条,与同段文本位置 caret 像素一致。**坑(折叠 placeholder `caret-color: transparent`)**:折叠段落里 `...` 是 inline atom,`caret-color: transparent` 只对"在 placeholder 内部"的虚拟位置生效(实际不能进入),对紧贴 placeholder 左右的位置**不**生效——但 `customCaretPlugin` 接管紧贴 placeholder 两侧的位置后,会切 `view.dom` 上的 `.velo-native-caret-off` class 显式把原生 caret 藏掉,这条 SCSS 与 plugin 协作闭环(详细见下)

- **阅读模式(readOnly)禁用"展开源码"交互 + 隐藏编辑类按钮**: `view.editable=false` 只挡用户输入,不挡 `appendTransaction` / `handleClick` / NodeView 事件。"光标进入/点击 → 显示源码字符"的交互(mark 源码编辑 / 链接单击 / 图片按钮 / 行内与块级公式编辑态 / mermaid toggle)在每个触发点读 `view.editable` 守卫;编辑类按钮(code 语言切换 / mermaid delete+toggle / TOC delete / task checkbox)用 CSS `.ProseMirror[contenteditable="false"]` 隐藏或禁点击,走 contenteditable 属性动态生效(无需 rebuild decorations / NodeView)。**坑**:`markSourceEditPlugin.appendTransaction` 无 view 参数,用模块级 `editorView` 引用(plugin spec `view()` 设、`destroy` 清)读 editable。保留:链接 Ctrl/Cmd 跳转、`ensureMermaidSourceVisibleAt`(查找替换)、复制按钮、TOC item link、footnote backref(导航 / 非编辑类)。脚注无 source/display 切换(label 是 text content),不纳入

- **专注模式 CSS 驱动 + plugin 只标记当前块**: `focusModePlugin` 开启时用 `Decoration.node` 给光标所在的**顶层块**(depth-1 祖先,blockquote 内段落高亮整个 blockquote)挂 `.velo-focus-active` class,降透明度由 CSS `.velo-editor.focus-mode .ProseMirror > *` → `opacity:.25` + `.velo-focus-active` → `opacity:1` 接管。plugin 不自己 dim 非活跃块(避免在每次光标移动时重建大量 Decoration),只管标记当前块一个 node decoration。容器 class(`.focus-mode`)由 `ProseMirrorEditor/index.vue` 的 prop 驱动,与 plugin 的 enabled state 经 `setMeta(focusModeKey)` 同步。源码模式(CM6)镜像同设计:`cmFocusModeField` StateField 跟踪当前段落(空行分隔),用两条 `Decoration.mark`(段前 + 段后)降透明度,O(1) decoration 量

- **打字机模式居中 defer 到 `requestAnimationFrame`,同步 scrollBy 会被覆盖**: `typewriterModePlugin` 开启时把光标所在行滚到滚动容器(`findScrollAncestor`)垂直中线。**关键坑**:不能在 plugin `view.update()` 里**同步** `scrollBy` —— `updatePluginViews()`(行 5527,plugin `view.update()` 在此跑)先于 PM 的 scroll 分支(行 5530-5538:`scrollToSelection` / `resetScrollPos`),也先于浏览器原生 `overflow-anchor`(布局期);同步 scrollBy 落在所有这些之前,会被带 `scrollIntoView` 标记的 tr(Enter / paste / find 命中 / TOC·大纲跳转 / crossModeSync placeCursor)的"最小滚入视口"或浏览器 scroll-anchoring 覆盖,光标被顶出视口 → "光标消失"。解法:居中走 `requestAnimationFrame`,在 PM 整个 `updateState` 返回之后、paint 之前跑,scrollBy 是最终结果(无抖动);同帧多次 update 只排一个 rAF,回调里读最新 state。**仍需 `props.handleScrollToSelection` 开启时返 `true`**:PM 的 `scrollToSelection` 不只滚编辑器容器,可能滚 window / 外层祖先(`scrollRectIntoView` 沿链向上),rAF 只居中编辑器容器撤不掉 window 滚动,故先抑制 PM 自身滚动(行 5546 `someProp` 命中即跳过)再 rAF 居中;关闭返 `false` 零回归。**不用 `scrollThreshold: Infinity`**:静态值无法随 enabled 翻转,`view.setProps` 又触发重挂。居中触发条件:`view.update()` 里 enabled 且 sel/doc 变化或 just-enabled(toggle-on 立即居中,defer 一帧),meta-only tr(find 高亮 / fold toggle)跳过。居中算法取选区垂直中点(collapse 选区取 head 行中线;NodeSelection 走 `nodeDOM` 真矩形 —— 见下条;范围选取 `from.top`→`to.bottom` 中点),祖先 `scrollBy(delta)`,阈值 4px 防亚像素抖动。**边界(有意接受)**:切文件后 `resetScrollToTop()` 覆盖居中(光标落顶,下次交互再居中),切标签 `restoreScrollTop()` 同理 —— 与"打开文件不抢视口"取舍一致。源码模式(CM6)镜像同坑同解:`EditorView.updateListener` 里**不**同步 `view.scrollDOM.scrollBy`(会被 CM6 自身 scrollIntoView 覆盖),改 `scheduleCenterCm` defer 到 rAF;enabled 用组件级 `let` 而非 StateField(typewriter 无 decoration),`onBeforeUnmount` 取消 pending rAF

- **打字机居中 NodeSelection 用 `nodeDOM` 真矩形,不能用 coordsAtPos(from/to) —— 修点击图片顶 ~1/4 视口**: 点击图片产生 NodeSelection。Velo 图片是 inline-atom,但 NodeView 的 wrapper 是 `display:block` 撑满行(模型 inline、渲染 block);`coordsAtPos(from)` 落在图片**上方**文本行、`coordsAtPos(to)` 落在图片**下方**文本行,二者中点偏向上下文本行而非图片本体 → 居中把图片往上顶约 1/4 视口。改用 `view.nodeDOM(sel.from).getBoundingClientRect()` 拿图片 wrapper 真实矩形取中点。collapse 文本选区 from===to 退化 head 行中线,范围选取 from.top→to.bottom 中点,行为不变

- **PM 切标签滚动位置保留:在 tabSwitchToken watch 同步捕获旧标签 state,不用 DOM scroll listener**: PM 不像 CM6 有 `viewportChanged` 信号,滚动是纯 DOM 行为不产生 transaction,`onSelectionChange` 不跑 → store 里的 `scrollTop` 停在上次选区变更(点击 / 键入)时的值。**不要用 `scroll` 事件 + rAF 捕获**:rAF 回调异步执行,用户快速切标签时 `activeDoc()` 已指向新标签但 `scrollTop` 还是旧标签的 → 把旧标签的位置写入新标签的 DocState(非激活文档位置被篡改);`restoreScrollTop` 触发的 scroll 事件也会被 rAF 捕获,PM 内部滚动管理可能在 rAF 回调前覆盖 `scrollTop` → 捕获到中间态 → 覆盖刚恢复的正确值(切回跳到顶部)。**正确解法**:在 `tabSwitchToken` watch(`flush:'sync'`)里,restore 新标签**之前**先把旧标签的 `view.state` + `scroller.scrollTop` 同步写回 store(`capturePmStateForDoc(prevActiveId, ...)`)。此时 `activeId` 已指向新标签,但 view 仍持有旧标签的 EditorState、滚动容器仍是旧标签的位置 —— 原子保存,无竞态。`prevActiveId` 在 `onReady` 初始化为 `documentStore.activeId`,每次 watch 末尾更新。**还需在 `modelValue` watch 的 `resetScrollToTop()` 后 + `onReady` 里各调一次 `captureActivePmState(view.state, 0)`**:文件装载走 `view.updateState(EditorState.create(...))` 而非 `dispatchTransaction`,`onSelectionChange` 不跑 → `pmState` 为 `undefined`,切回时 `peekActivePmStateForRestore` 返回 null → 走重建 + `resetScrollToTop`。CM6 侧对称实现(`captureCmStateForDoc` + `prevActiveId`),额外在 `setState` + `scrollTop` 后 recapture 一次修正 `updateListener` 在 `setState` 期间用旧 `scrollTop` 的误捕

- **PM 滚动容器必须 `overflow-anchor: none`,否则浏览器原生 scroll-anchoring 覆盖 `restoreScrollTop`**: `view.updateState(cachedState)` 整体替换文档 DOM 后,`restoreScrollTop(cached.scrollTop)` 在 JS 同步阶段设好正确值,但浏览器在随后的**布局阶段**会执行原生 scroll-anchoring —— 它在旧 DOM 上选了锚点元素、在新 DOM 里找对应元素、按位置差补偿 `scrollTop`,覆盖 JS 设的值。表现:切标签偶发滚动位置偏移(非每次必现,取决于新旧文档结构差异和切换时的滚动位置)。CM6 的 `.cm-scroller` 内置 `overflow-anchor: none`(CM6 自身样式),PM 侧滚动容器(`ProseMirrorEditor/index.vue` 的 `overflow-auto` div)缺这条。修复:在 `.velo-scroll` CSS 规则(`index.scss`)统一加 `overflow-anchor: none` —— 所有用了 `v-velo-scroll` 的滚动容器都是 JS 程序化管理滚动位置的,浏览器不应干预

- **foldDecoration 跨标签 state swap 的位置越界守卫**:`view.updateState(cachedState)` 整体替换 EditorState 时,PM **不调 `apply`**,只调 `view.update`。`foldDecoPlugin.view.update` 的 `prevCollapsed` 闭包仍持有**上一个标签**的折叠 pos,diff 同步逻辑会拿旧标签 pos 在新标签 doc 上调 `makeStableKeyForPos` → `doc.nodeAt(pos)` 抛 `Position X outside of fragment`。三处守卫:① `makeStableKeyForPos` 在 `nodeAt` 前做 `pos < 0 || pos > doc.content.size` bounds check;② `recomputeFoldedCodeBlockPos` 在 `doc.resolve` 前做同样 check;③ `view.update` 检测 `prevCollapsed` 中有越界 pos 时判定为 state swap,直接重置 `prevCollapsed = new Set(s.collapsedSet)` 并跳过 diff(避免误写 fold store)。`view.updateState` 路径被 `capturePmStateForDoc` 确保 `pmState` 始终 fresh 后成为常态路径,这些守卫是必须的

- **`pendingPmDoc` 消费跳过冗余 fromMarkdown(C0) + 大文档延迟 fromMarkdown(C3) + Worker 异步 parse(C1)**: `loadContentInto` 在 `documentStore` 层做 `fromMarkdown(c, schema)` 拿到 PM Node 后,存入 `DocState.pendingPmDoc`(`markRaw` 包裹)。`EditorInner` 的 modelValue watch 与 `useProseMirror` 的 `fromMarkdown` 回调均通过 `documentStore.consumePendingPmDoc()` 一次性消费——有 pending 则直接用,无则 fallback 到 `fromMarkdown(newVal, schema)`。两条消费路径互斥:初始装载走 `useProseMirror` 回调(组件首挂 + modelValue watch 不 fire);后续切文件 / fs:watch 走 modelValue watch。消费后置 `undefined`,不影响后续路径。打开链路 markdownIO 调用从 3 次(`fromMarkdown` × 2 + `toMarkdown` × 1)降到 2 次(小文档)或 1 次(大文档 + C0b 跳过 canonical)。**C3**:大文档(> 2000 行)进一步跳过 `loadContentInto` 里的同步 `fromMarkdown`——不设 `pendingPmDoc`,`modelValue` watch 的 fallback 在 rAF 后执行 `fromMarkdown`。rAF 确保浏览器先 paint loading 遮罩(`docLoading` ref + Tailwind `animate-spin` overlay)再执行 parse。**C1**:大文档的 `fromMarkdown` 替换为 `fromMarkdownAsync`——`processor.parse(md)` + `processor.runSync(tree)` 移入 `markdownWorker.ts`(Web Worker),主线程不阻塞;Worker 返回 mdast JSON 后,主线程执行 `mdastToPMDoc`(`annotateMathDelimiterCount` + `annotateEmphasisMarker` + `mdastBlockToPM`,需要 schema + md 原文,不能在 Worker 做)。parse processor 配置抽成 `parseProcessor.ts` 的 `createParseProcessor()`,Worker 和主线程共用(主线程额外追加 `remarkStringify`)。Worker 创建失败 / parse 报错 / 超时(10s)自动降级到同步 `fromMarkdown`。**取消机制**:`modelValue` watch 用 `parseToken` 递增令牌——快速切 tab 时旧 Worker parse 结果被丢弃(`myToken !== parseToken` 检查)。`useProseMirror` 冷启动路径的 `fromMarkdown` 回调可返回 `PMNode | Promise<PMNode>`,`Promise.resolve(result).then(...)` 统一处理 sync / async;`view.isDestroyed` 检查覆盖取消。效果:大文档打开期间主线程不冻结,spinner 可交互(滚动 tab / 点菜单)

- **表格对齐是列级操作,走整表 replaceWith**:`setCellAlignment` 把光标所在列的 **所有 cell**(header + 全部 body 行)一起改 alignment。实现复用 `findTableWrapper`(`$from.start(d) - 1` 对齐 descendants 语义)+ `findColIndex`(Fragment.forEach 第三个参数才是列 index)+ `rowIndexForSelection`,逐行 `cell.type.create({ ...attrs, alignment }, cell.content)` 改目标列 cell(content 原样保留),其余列原样复用,最后整表 `replaceWith` + `dispatchReplaceWithCursor` 把光标停在原 cell。为什么不用逐 cell `setNodeMarkup`:GFM 对齐全列同值(`markdownIO` 的 `pmTableToMdast` 只从首行推导 `align[]`,列内值一致 round-trip 才闭合),逐 cell 改既做错又冗余。**对齐持久化走 GFM 分隔行 `|:---:|`,无需外挂文件**——左/中/右三种原语 `pmTableToMdast` / `mdastTableToPM` 双向 round-trip。**CellSelection 矩形内右键**:`setCellAlignment(align, clickCellPos)` 当 `selection instanceof CellSelection` 且落在矩形内时,以 `columnsOfCellSelection(TableMap.findCell)` 取矩形覆盖的 **所有列** 一起对齐(非覆盖列不动),达成"矩形内任意格右键 = 覆盖所有列一起变";否则按 anchor 所在列对齐(兼容单 cell / 无锚点)

- **CJK 排版两层架构(v0.7.7)**: 分实时输入层 + 手动格式化层(见 DECISIONS ADR-20260805-001)。**实时层**三个插件在 `order.ts` 末尾依次排列:`cjkLetterSpacing`(纯装饰,无输入拦截)→ `cjkAutoFormat`(`handleTextInput` 拦截单字符做全角标点 / 中英文间距 / 智能引号)→ `autoPair`(`handleTextInput` 拦截 CJK 开括号做配对)。`cjkAutoFormat` 在 `autoPair` **之前**:智能引号转换可能把键入的 `'` 变成 `"` 或 `「`,需要先于 autoPair 的括号配对逻辑判定;但 autoPair 的闭括号跳越(Tab / Shift+Tab)不与 cjkAutoFormat 冲突(跳越只移光标不插字符)。**手动层**走 `cjkFormatter/` 库(`src/lib/cjkFormatter/`),命令触发时逐块 `toMarkdown → formatMarkdown → fromMarkdown` 往返,保 undo / 光标;与实时层部分规则重叠(中英文间距等),用户可分别开关各子项。两层正交:关掉实时层不影响手动格式化,反之亦然。**设置项分两组**:`editor.cjkLetterSpacing` + `editor.autoPairEnabled` 控制实时层开关;`editor.cjkFormatting.*`(20+ 子项)控制手动格式化规则集 + 实时层的全角标点 / 智能引号 / 中英文间距子项。
- **`liftListItem` 在 list_item 嵌套 block 中误匹配(list 降级坑)**: Enter 链中 `liftListItem` 的设计意图是"空 list_item 按 Enter 退出列表"(splitListItem 在空 list_item 返回 false,不能 fall back 到 splitBlock 否则 list_item 里开新 paragraph 与有内容时的行为割裂)。但 `liftListItem` 的 `blockRange` 谓词是"节点首子是 list_item",它匹配到 **bullet_list / ordered_list** 层而非 list_item 层;当光标在 `list_item > blockquote > paragraph`(或 alert 等任何嵌套 block)中时,splitListItem 不匹配(`$from.node(-1)` 是 blockquote 不是 list_item),liftListItem 错误匹配并调 `liftOutOfList` 把整个 list_item 提升出 list —— 用户感知"list 降了一级"。修复:在 splitListItem 和 liftListItem 之间插入 `splitInListItemNestedBlock` 守卫,检测光标在 list_item 内的非首层 paragraph(即 list_item 的嵌套 block 子节点)中时:空段落走 `liftEmptyBlock`(提升出嵌套 block,与顶层 blockquote 退出行为一致),非空走 `splitBlock`(在嵌套 block 内正常分裂段落)。与 `emptyParaBeforeListBackspace`(Backspace 链中列表下方空段落守卫)同款范式:都是在 PM 默认命令误操作 list 结构前提前拦截。**注意**:守卫检查"list_item 直接子节点是否为 paragraph"来区分"首层 paragraph(应走 splitListItem / liftListItem)"与"嵌套 block 内(应走守卫)",依赖 list_item content `'paragraph block*'` 约束(首子必须是 paragraph)
- **空段落退出 block(blockquote / alert)与 code_block 退出**: PM 的 `liftEmptyBlock`(空 textblock 按 Enter 提升出父节点)被 `baseKeymap` 的 Enter 链绑定,但自定义 Enter 链排在 `baseKeymap` 之前且 `splitBlock` 会先消费(空段落分裂出另一个空段落,返回 true),导致用户被困在 blockquote / alert 内永远出不来。修复:在自定义 Enter 链 `splitBlock` **之前**加入 `liftEmptyBlock`,让空段落优先提升出父节点。**`splitInListItemNestedBlock` 同步更新**:list_item 内嵌套 block 的空段落也走 `liftEmptyBlock` 而非 `splitBlock`,与顶层 blockquote 退出行为一致(提升出嵌套 block 但留在 list_item 内)。**code_block 不走 `liftEmptyBlock`**(code_block 是 `text*` 不是 textblock,无内嵌 paragraph),改用 **Shift-Enter** 退出:`codeBlockExit` 在 Shift-Enter 链首位拦截,在 code_block 后插入空段落并将光标移入。Enter 在 code_block 内永远只插 `\n`(保持当前行为),用户可自由写多行空行不被意外踢出。与 table cell 的 Shift-Enter 插 `<br>` 同键位族(都是"Enter 的变体"),语义不冲突(code_block 内 `cmdTableCellHardBreak` return false)。**表格不适用**:表格的 Enter 由 `cmdTableCellEnter` 拦截(跳下一行 / 末行追加行),不走到 `liftEmptyBlock`;退出表格靠 Tab 或点击表格外
- **Shift-Enter 多场景命令链(v0.7.7)**: Shift-Enter 从"仅 table cell 插 `<br>` + code_block 退出"扩展为多场景命令链,按顺序短路:`codeBlockExit`(code_block 内跳出)→ `cmdTableCellHardBreak`(table cell 内插 `<br>`)→ `shiftEnterExitBlock`(blockquote / alert 内退出:空段落走 `liftEmptyBlock` 提升出 block,非空在 block 后插入空段落并将光标移入)→ `shiftEnterListItem`(list_item 首层 paragraph 内直接 `splitBlock`,产生缩进段落,等同 Enter+Backspace 的效果但不创建新 list_item)→ `splitBlock`(兜底,普通段落 / heading / 嵌套 block 内正常换行)。**设计要点**:`shiftEnterExitBlock` 必须区分空 / 非空段落——空段落如果在 block 后再插一段会残留 block 内空段 + block 外空段,改用 `liftEmptyBlock` 提升空段落出 block,与 Enter 退出行为一致;`shiftEnterListItem` 只匹配 list_item 的**首层** paragraph(list_item 直接子节点是 paragraph),嵌套 block 内的 Shift-Enter 走兜底 `splitBlock`(在嵌套 block 内换行,不退出);`shiftEnterListItem` 跳过 `splitListItem`(Enter 创建新 list_item,Shift-Enter 不创建)。**不适用**:heading 的 Shift-Enter 走兜底 `splitBlock`,PM 默认行为是分裂后第二个节点变成 paragraph(非 heading)

## 新增语法支持 checklist

> 一条新语法落地，需要 check 一遍涉及哪些层避免遗漏。
> checklist 不是规约，多数简单语法只碰其中 2-3 个文件。


| # | 涉及层 | 文件 | 何时需要动 |
|---|--------|------|-----------|
| 1 | **schema** | `editor/schema.ts` | 新增节点类型 / mark / attrs |

| 5 | **syntax registry**(实时键入) | `syntax/{block，inline}/*.ts` + `syntax/index.ts` | 用户键入也要转(块级 / 行内带匹配) |
| 6 | **ProseMirror 插件** | `EditorInner.vue` 的 `pluginEntries` + `plugins/order.ts` | 需要新装饰 / 行为插件(查找高亮 / 自动补全 / 原子保护);新增插件须同时在 `order.ts` 加 id |

| 10 | **ARCHITECTURE** | `docs/architecture/editor.md`（必要时联动 `docs/ARCHITECTURE.md` 路由） | 跨节点依赖 / 触发时机反直觉 / 新黑名单维度 / 非显然设计取舍；**纯模板化不需要改** |

**容易遗漏的项**:
- 第 5 列注册——`syntax/index.ts` 没 `registerXxx` = 不生效，且无警告，纯静默
- 第 4 列双向——`fromMarkdown` 加了，`toMarkdown` 忘了，文件保存再加载会丢数据
- 第 9 列留痕——发版时该语法的 feat/fix 走 `git log` 即可；属用户可见变更按分组写入 RELEASE_NOTES，属"重大决策"取舍另写入 DECISIONS ADR 块（"为什么走 X 不走 Y"不写在 commit message 里）
- 第 10 列过度——简单语法也写一段架构说明反而稀释文档信号

- `[TOC]` 涉及 schema + Decoration.widget(TocDecoration) + markdownIO 双向 + syntax/block/toc + 注册(无 NodeView / 无 remark)
- `:smile:` emoji 短码 涉及 schema(`emoji` inline atom 节点,`attrs.shortcode`)+ remark(remarkEmoji 在 mdast text 节点内切 `:shortcode:` 段,查 `node-emoji` 表验证合法性)+ markdownIO 双向(fromMarkdown emoji mdast 节点 → PM emoji node;toMarkdown emoji node → `:shortcode:` html 边界,防 `:` 被 escape)+ NodeView(EmojiNodeView 查 node-emoji 表渲染 Unicode char,无选中态外框线)+ syntax/inline/emoji + 注册(在 htmlTag 之前)+ emojiSuggestPlugin(`:short` 输入态自动补全下拉,node-emoji search 模糊匹配)+ emojiSourceEditPlugin(光标靠近 emoji → appendTransaction 替换为 `:shortcode:` 源码文本可编辑 + 源码左侧渲染 emoji 预览 widget Decoration.widget side:-1,同 imageEdit 预览范式;移出 commit 重建 emoji;Escape 还原)。导出 walker 补 `case 'emoji'` 输出 Unicode char。短码可逆:round-trip `:smile:` → emoji node → `:smile:` 严格 idempotent。atom 节点 `marks:''`,emoji 在 link 内会被拉出(与 image 同款已知限制)
